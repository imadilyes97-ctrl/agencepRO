# Module 13 — Multi-Agences

## 13.1 Objectif

Permettre a une entreprise (holding, groupe, franchise) de gerer plusieurs agences de voyages depuis une seule instance SaaS, avec isolation stricte des donnees, reporting consolide, et gestion centralisee des plans de facturation.

Ce module est accessible uniquement aux plans **Pro** (3 agences max) et **Enterprise** (illimite). Le plan **Starter** est mono-agence.

## 13.2 Architecture Tenant

### 13.2.1 Principe fondamental

Chaque agence est un **tenant isole**. Aucune agence ne peut jamais acceder aux donnees d'une autre agence, meme indirectement.

### 13.2.2 Isolation au niveau base de donnees

Methode : **PostgreSQL RLS (Row Level Security)** sur chaque table contenant des donnees d'agence.

```
Mecanisme :
1. Chaque table metier (clients, dossiers, factures, documents, etc.)
   possede une colonne `agence_id` NOT NULL avec index.

2. A chaque connexion, le middleware applicatif definit :
   SET app.current_agence_id = '<agence_id_du_user>';
   SET app.current_role = '<role_du_user>';

3. Les policies RLS filtrent automatiquement :
   - Les agents ne voient QUE les lignes de leur agence
   - Le Super Admin voit TOUT (bypass RLS)
   - Les agents inter-agence ne voient rien

4. Le role applicatif PostgreSQL utilise :
   - agence_pro_user (lecture/ecriture scope tenant)
   - agence_pro_admin (Super Admin uniquement, bypass RLS)
```

### 13.2.3 Schema RLS — Policies par table

```sql
-- Exemple pour la table clients (appliquee a chaque table metier)

-- Policy 1 : Isolation par agence (defaut pour tous les roles sauf Super Admin)
CREATE POLICY tenant_isolation ON clients
  FOR ALL
  USING (agence_id = current_setting('app.current_agence_id')::text)
  WITH CHECK (agence_id = current_setting('app.current_agence_id')::text);

-- Policy 2 : Super Admin bypass — acces complet
CREATE POLICY super_admin_access ON clients
  FOR ALL
  USING (current_setting('app.current_role') = 'SUPER_ADMIN');

-- Policy 3 : Lecture seule pour les managers cross-agence (si applicable)
CREATE POLICY manager_read_only ON clients
  FOR SELECT
  USING (
    current_setting('app.current_role') = 'MANAGER'
    AND agence_id IN (
      SELECT agence_id FROM user_agence_assignations
      WHERE user_id = current_setting('app.current_user_id')::text
    )
  );
```

Tables couvertes par RLS (toutes les tables metier) :

| Table | Colonne cle | Type d'acces isole |
|-------|-------------|-------------------|
| `clients` | `agence_id` | CRUD |
| `dossiers` | `agence_id` | CRUD |
| `factures` | `agence_id` | CRUD |
| `paiements` | `agence_id` | CRUD |
| `documents` | `agence_id` | CRUD |
| `vols` | `agence_id` | CRUD |
| `hotels` | `agence_id` | CRUD |
| `groupes` | `agence_id` | CRUD |
| `depenses` | `agence_id` | CRUD |
| `historique_actions` | `agence_id` | Read |
| `notifications` | `agence_id` | Read |
| `users` | `agence_id` | Read (profil) |

### 13.2.4 Isolation au niveau applicatif

Au-dela du RLS, le middleware applicatif applique un second filtre :

```typescript
// middleware.ts — Chaque requete API ou Server Action
// 1. Verifie le JWT de la session
// 2. Extrait agenceId du token
// 3. Injecte le contexte tenant dans chaque requete Prisma

const prisma = new PrismaClient().$extends({
  query: {
    $allOperations({ args, query }) {
      // Injection automatique de l'agence_id sur les operations d'ecriture
      if (['create', 'updateMany', 'deleteMany'].includes(operation)) {
        args.data = { ...args.data, agenceId: session.agenceId };
      }
      return query(args);
    }
  }
});
```

### 13.2.5 Regles metier d'isolation

| Regle | Description |
|-------|-------------|
| **R13-ISO-01** | Aucune donnee d'une agence n'est accessible a une autre agence, meme en lecture |
| **R13-ISO-02** | Le Super Admin peut lire toutes les donnees, mais ne peut pas les modifier hors de son scope |
| **R13-ISO-03** | Les transferts de dossier entre agences sont traces et necessitent une validation Super Admin |
| **R13-ISO-04** | Les logs d'audit sont stockes dans une table separate sans RLS (accessible Super Admin uniquement) |
| **R13-ISO-05** | Les sauvegardes sont isolees par agence (meme physique, isolation logique) |

### 13.3.6 Flux de creation

```
Super Admin → /admin/agences/nouvelle
    → Remplit le formulaire
    → Upload logo
    → Click "Creer"
    → Backend :
        1. Validation Zod (tous les champs)
        2. Verification RC + NIF (UNIQUE constraint)
        3. Creation record Agence (statut: EN_ATTENTE)
        4. Creation espace stockage Supabase
        5. Generation sous-domaine DNS
        6. Creation compte Super Admin de l'agence (email temporaire)
        7. Email de bienvenue envoye
        8. Log audit creation
    → Retour : Confirmation + demande de validation
    → Super Admin → Valide ou rejette
```

# Module 14 — Signature Electronique

## 14.1 Objectif

Permettre la signature electronique de contrats et documents juridiques directement dans l'application, conforme a la legislation algerienne **Loi 18-05 du 25 septembre 2018** relative a la signature electronique.

## 14.2 Conformite Legale

### 14.2.1 Loi 18-05 (Algerie)

La Loi 18-05 definit la signature electronique comme « toute donnee sous forme electronique, jointe ou logiquement associee a d'autres donnees sous forme electronique, et qui est utiliseee pour identifier la personne dont proviennent ces donnees ».

### 14.2.2 Conditions de validite

| Condition | Implementation Agence Pro |
|-----------|--------------------------|
| **Identification du signataire** | Verification OTP (email + SMS) prealable a la signature |
| **Intention de signer** | Bouton explicite « Je signe » + mention legale affichee |
| **Lien avec le document** | Hash SHA-256 du document lie a la signature |
| **Integrite du document** | Hash SHA-256 genere AVANT et APRES signature (verification anti-falsification) |
| **Horodatage certifie** | Timestamp serveur + horodatage NTP |
| **Conservation** | Archive legale 10 ans minimum (obligation legale) |
| **Traçabilite** | Journal d'audit complet : qui, quand, depuis ou, IP, device |

### 14.2.3 Valeur juridique

La signature electronique Agence Pro a la **meme valeur probante** qu'une signature manuscrite devant les tribunaux algeriens, a condition de respecter les 7 conditions ci-dessus.

### 14.2.4 Mentions legales affichees

```
En signant ce document, vous atteste que :
1. Vous avez pris connaissance de l'integralite du document
2. Vous acceptez librement les termes et conditions
3. Vous reconnaissez que cette signature electronique a la meme valeur
   qu'une signature manuscrite conformement a la Loi 18-05 du 25 septembre 2018
4. Le document signe est horodate et ne peut plus etre modifie
```

## 14.3 Documents Signables

| Document | Declencheur | Signataires requis | Modele |
|----------|-------------|-------------------|--------|
| **Contrat de voyage** | Creation dossier Confirme | Client + Agent (ou Admin) | Template generique ou personnalise |
| **Conditions Generales (CGV)** | A chaque nouveau dossier | Client uniquement | Template agence |
| **Autorisation parentale** | Mineur dans le dossier | Parent/Legal tuteur | Template standard |
| **Mandat de paiement** | Paiement par tiers | Client + Tiers payeur | Template standard |
| **Devis accepte** | Acceptation d'un devis | Client | Template agence |
| **Attestation d'assurance** | Souscription assurance | Client + Agent | Template assurance |

## 14.4 Workflow de Signature

### 14.4.1 Vue d'ensemble

```
PREPARE → ENVOYE → ACCUSE_RECEPIT → EN_COURS_SIGNATURE → SIGNE → ARCHIVE
                                                         ↓
                                                    REFUSE / EXPIRE
```

### 14.4.2 Etape 1 — PREPARATION

**Declencheur** : L'Agent ou l'Admin prepare le document pour signature.

| Champ | Type | Description |
|-------|------|-------------|
| `typeDocument` | Enum | CONTRAT_VOYAGE / CGV / AUTORISATION_PARENTALE / MANDAT_PAIEMENT / DEVIS |
| `dossierId` | String | Dossier associe (optionnel) |
| `clientId` | String | Client principal |
| `signataires` | Array | Liste des personnes devant signer |
| `messagePersonnalise` | Text | Message accompagne le document (optionnel) |
| `dateExpiration` | Date | Date limite de signature (defaut: 15 jours) |
| `modelesPersonnalises` | Object | Champs a injecter dans le template |

**Donnees du document genere :**

| Champ | Source | Description |
|-------|--------|-------------|
| `documentId` | Auto-gene | Identifiant unique du document |
| `contenuHTML` | Template + donnees | HTML genere a partir du template |
| `hashInitial` | SHA-256 | Hash du contenu avant signature |
| `version` | 1 (defaut) | Version du document |
| `statut` | PREPARE | Etat initial |

### 14.4.3 Etape 2 — ENVOI

**Declencheur** : L'Admin/Agent envoie le document pour signature.

| Action | Description |
|--------|-------------|
| Generation du PDF | Le HTML est converti en PDF |
| Envoi email | Lien de signature envoye a chaque signataire |
| Envoi SMS | SMS avec lien court (optionnel) |
| Notification in-app | Alerte dans le portail client |
| Demarrage timer | Date d'expiration demarree |

**Donnees de l'envoi :**

| Champ | Type | Description |
|-------|------|-------------|
| `envoyePar` | String | ID de l'expediteur |
| `dateEnvoi` | DateTime | Horodatage d'envoi |
| `canalEnvoi` | Enum | EMAIL / SMS / LES_DEUX |
| `lienSignature` | URL | Lien unique et securise (token JWT) |
| `expirationSignature` | DateTime | Date limite de signature |

### 14.4.4 Etape 3 — VERIFICATION D'IDENTITE (OTP)

**Declencheur** : Le signataire ouvre le lien de signature.

**Verification en deux etapes :**

#### Etape 3a — Verification par email

| Etape | Description |
|-------|-------------|
| 1 | Le signataire ouvre le lien |
| 2 | Une page s'affiche demandant la verification |
| 3 | Un code OTP (6 chiffres) est envoye a l'adresse email du signataire |
| 4 | Le signataire saisit le code |
| 5 | Verification en temps reel (expiration: 5 minutes) |

#### Etape 3b — Verification par SMS (renforcement)

| Etape | Description |
|-------|-------------|
| 1 | Apres validation OTP email |
| 2 | Un deuxieme code OTP (6 chiffres) est envoye par SMS au telephone du signataire |
| 3 | Le signataire saisit le deuxieme code |
| 4 | Validation double = identite confirmee |

**Regles OTP :**

| Regle | Description |
|-------|-------------|
| **R14-OTP-01** | Chaque code OTP expire apres 5 minutes |
| **R14-OTP-02** | Maximum 3 tentatives par code |
| **R14-OTP-03** | Apres 3 echecs, le lien de signature est bloque 30 minutes |
| **R14-OTP-04** | Un nouveau code peut etre demande apres 60 secondes |
| **R14-OTP-05** | Les codes OTP sont generes de maniere cryptographiquement securisee |
| **R14-OTP-06** | Le code est a usage unique (consomme apres validation) |
| **R14-OTP-07** | La verification OTP est enregistree dans le journal d'audit |

### 14.4.5 Etape 4 — PAGE DE SIGNATURE

**Declencheur** : Apres verification OTP reussie.

#### Affichage de la page

| Element | Description |
|---------|-------------|
| Document PDF | Affichage integral du document (scroll obligatoire) |
| Zone de signature | Canvas interactif pour dessiner la signature |
| Mention legale | Texte de la loi 18-05 affiche avant signature |
| Bouton "Je signe" | Activation apres lecture + signature dessinee |
| Bouton "Refuser" | Possibilite de refuser (avec motif obligatoire) |
| Compteur temps | Temps passe sur le document (minimum 10 secondes) |

#### Zone de signature (Canvas)

| Fonctionnalite | Description |
|----------------|-------------|
| Dessin libre | Souris ou doigt (tablette/mobile) |
| Epaisseur du trait | 2px par defaut, ajustable |
| Couleur du trait | Noir (#000000) par defaut |
| Effacer | Bouton pour recommencer |
| Valider | Capturer la signature comme image PNG |
| Taille minimum | La zone fait au moins 300x100 pixels |
| Resolution | Signature stockee en 600 DPI |

**Regles de la zone de signature :**

| Regle | Description |
|-------|-------------|
| **R14-SIG-01** | La signature doit faire au moins 10 pixels de large |
| **R14-SIG-02** | La zone est activee uniquement apres scroll complet du document |
| **R14-SIG-03** | Le "temps minimum de lecture" (10s) empeche la signature rapide |
| **R14-SIG-04** | La signature est capturee comme image vectorielle PNG |
| **R14-SIG-05** | La signature est liee au hash du document |

### 14.4.6 Etape 5 — SIGNATURE EFFECTIVE

**Declencheur** : Le signataire clique sur "Je signe".

**Operations en arriere-plan :**

```
1. Capture de la signature canvas (PNG)
2. Calcul du hash SHA-256 du document
3. Verification que le hash = hash initial (integrite)
4. Liaison signature + hash + timestamp dans un bloc signe
5. Generation du PDF signe (document + signature + certificat)
6. Horodatage : date + heure UTC + timezone du signataire
7. Enregistrement dans la base :
   - signatureId (cuid)
   - documentId
   - signataireId
   - signatureImage (PNG stocke)
   - hashDocument (SHA-256)
   - hashSignature (SHA-256 de la signature)
   - timestampSignature (DateTime UTC)
   - adresseIP
   - userAgent (device, navigateur)
   - otpValide (true)
8. Si tous les signataires ont signe → statut = SIGNE
9. Sinon → statut = EN_COURS_SIGNATURE (en attente des autres)
10. Email de confirmation envoye au signataire
11. Email de notification envoye a l'agent/admin
```

**Donnees de la signature :**

| Champ | Type | Description |
|-------|------|-------------|
| `signatureId` | String | ID unique de la signature |
| `documentId` | String | Document signe |
| `signataireId` | String | ID du signataire |
| `signatureImage` | Binary | Image PNG de la signature |
| `hashDocument` | String (SHA-256) | Hash du document au moment de la signature |
| `hashSignature` | String (SHA-256) | Hash de l'image signature |
| `timestampSignature` | DateTime | Horodatage exact de la signature |
| `adresseIP` | String | IP du signataire |
| `userAgent` | String | Navigateur + device |
| `otpEmailValide` | Boolean | OTP email valide |
| `otpSmsValide` | Boolean | OTP SMS valide |
| `positionGeo` | Object | Position geographique (si autorisee) |

### 14.4.7 Etape 6 — ARCHIVAGE

**Declencheur** : Tous les signataires ont signe.

**Operations d'archivage :**

| Operation | Description |
|-----------|-------------|
| Generation PDF final | PDF avec toutes les signatures integrees |
| Ajout certificat | Page de certification avec hash, timestamp, signataires |
| Stockage archivage | Fichier stocke dans Supabase Storage (dossier archive/) |
| Indexation | Document indexe pour recherche rapide |
| Notification | Email a tous les signataires avec copie PDF |
| Lien permanet | URL de consultation permanente |
| Verrouillage | Le document ne peut plus etre modifie |
| Retention | Conservation 10 ans minimum (obligation legale) |

**Structure d'archivage :**

```
supabase-storage/
├── {agenceId}/
│   ├── archives-legales/
│   │   ├── {annee}/
│   │   │   ├── {mois}/
│   │   │   │   ├── {documentId}/
│   │   │   │   │   ├── document-original.pdf
│   │   │   │   │   ├── document-signe.pdf
│   │   │   │   │   ├── certificat-signature.json
│   │   │   │   │   ├── signatures/
│   │   │   │   │   │   ├── signataire-1.png
│   │   │   │   │   │   └── signataire-2.png
│   │   │   │   │   └── audit-trail.json
```

## 14.5 Horodatage et Integrite

### 14.5.1 Horodatage

| Element | Valeur | Source |
|---------|--------|--------|
| Date signature | YYYY-MM-DD HH:MM:SS | Serveur (NTP) |
| Timezone | Africa/Algiers (UTC+1) | Systeme |
| Format | ISO 8601 | Standard |
| Precision | Millisecondes | Serveur |
| Reference externe | RFC 3161 (optionnel) | TSA externe |

### 14.5.2 Hash SHA-256

| Element | Description |
|---------|-------------|
| Hash du document | Calcule AVANT injection de la signature |
| Hash de la signature | Calcule sur l'image PNG de la signature |
| Hash compose | SHA-256(document_hash + signature_hash + timestamp) |
| Stockage | Dans la table signatures ET dans le JSON du certificat |
| Verification | A tout moment, re-calculer le hash et comparer |

# Module 15 — QR Code

## 15.1 Objectif

Generer et gerer des QR codes pour identifier rapidement les clients, dossiers, billets et paiements, accessibles via le scanner de l'app mobile ou le portail client.

## 15.2 Types de QR Codes

### 15.2.1 QR Code Client

**But** : Identification rapide d'un client lors d'un check-in, d'une verification ou d'une interaction en personne.

#### Declencheur de generation

| Evenement | Description |
|-----------|-------------|
| Creation client | QR code genere automatiquement a la creation |
| Mise a jour profil | QR code regenere si informations critiques changent |
| Demande manuelle | L'Agent/Admin genere/regenere depuis la fiche client |
| Impression carte | QR code inclus sur la carte client |

#### Donnees encodees dans le QR

| Champ | Type | Description |
|-------|------|-------------|
| `clientId` | String | ID unique du client (chiffre) |
| `token` | String | Token temporaire signe (JWT, expiration 30 jours) |
| `agenceId` | String | ID de l'agence (pour routing) |
| `type` | Constant | "CLIENT" |
| `version` | Number | Version du QR (1 par defaut) |

**Structure du payload :**

```json
{
  "t": "client",
  "c": "encrypted_client_id",
  "a": "encrypted_agence_id",
  "v": 1,
  "exp": "2026-08-23T00:00:00Z",
  "sig": "sha256_hmac_signature"
}
```

#### Donnees affichees au scan

| Champ | Source | Affichage |
|-------|--------|-----------|
| Nom complet | `prenom` + `nom` | "Mohamed Benali" |
| Telephone | `telephone` | "+213 555 123 456" |
| Email | `email` | "mohamed@example.com" |
| Nationalite | `nationalite` | "Algerien" |
| Dossiers actifs | Requete | Nombre + type (ex: "2 dossiers actifs: Omra, Visa") |
| Photo | `photo` | Avatar (si disponible) |
| Derniere activite | `updatedAt` | Date de derniere modification |
| Statut | `statut` | ACTIF / INACTIF / SUSPENDU |

#### Regles metier

| Regle | Description |
|-------|-------------|
| **R15-QRC-01** | Le QR client est genere automatiquement a la creation du client |
| **R15-QRC-02** | Le token JWT expire apres 30 jours (renouvellement auto) |
| **R15-QRC-03** | Le scan est accessible uniquement par les roles: Admin, Manager, Agent, Guide |
| **R15-QRC-04** | Le client lui-meme peut scanner son propre QR depuis le portail |
| **R15-QRC-05** | Les donnees affichees ne contiennent JAMAIS de donnees sensibles (pas de passeport, pas de CNI) |
| **R15-QRC-06** | Chaque scan est journalise (qui a scanne, quand, depuis quel device) |
| **R15-QRC-07** | Le QR est unique par client (pas de doublon) |

#### Roles autorises

| Role | Genere | Scanne | Voit les donnees |
|------|--------|--------|------------------|
| Super Admin | Oui | Oui | Tout |
| Admin | Oui | Oui | Son agence |
| Manager | Non | Oui | Son agence |
| Agent | Non | Oui | Ses clients assigns |
| Guide | Non | Oui | Ses groupes assigns |
| Client | Non | Oui | Son propre QR |

### 15.4.3 Regles d'impression

## 15.8 Securite

| Mesure | Description |
|--------|-------------|
| Tokens JWT signes | Tous les QR contiennent un JWT HMAC-SHA256 |
| Expiration temporelle | Chaque QR a une date d'expiration |
| Scope agence | Le QR ne fonctionne que dans le scope de l'agence |
| Audit trail | Chaque scan est journalise |
| Pas de donnees sensibles | Le QR ne contient jamais de mots de passe, CNI, RIB |
| Rate limiting | Maximum 10 scans par minute par utilisateur |
| Chiffrement du payload | Le contenu sensible est chiffre avant encodage |
